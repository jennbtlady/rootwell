# Phase 3: Import wizard

Status: done on 2026-10-20, branch `phase-3/import-wizard`.

## Acceptance

- API test (`packages/api/test/imports.test.ts`): 5,000 rows of people plus gifts upload,
  map, match, commit and roll back in about 24 seconds. Rollback leaves zero gifts and
  only the person who existed before.
- Browser test (`apps/web/e2e/phase-3-import.spec.ts`): the same 5,000-row file through
  the real wizard in about 41 seconds, and a messy file through every step with
  accessibility scans, ending in a rollback.
- The messy fixture covers a duplicated person with different email case, a bad email
  fixed in place, a refund, a zero amount, an unreadable date, a future date, a short
  phone (dropped with a warning), an unknown payment method (recorded as Other), new
  funds and campaigns created by name, and an automatic match to an existing donor.
- Fixtures are generated by `packages/api/test/fixtures/import-fixture.ts`; the CSVs in
  `apps/web/e2e/fixtures` come from `write-csv.ts` in the same folder. Invented people.

## Known limits

- Commit runs in one request. Fine locally and for files up to the 50,000-row cap on a
  long-running server; on Vercel's default function timeout, large commits should move to
  a background job (Inngest) when hosting is set up in Phase 0 task 10.
- Starter mappings use the export headers as best known. The integrations research
  (`docs/integrations-research.md`) may correct them; auto-suggest covers small differences.
- Matched people are not updated from the file, only given gifts.

Brief: CSV and XLSX. Step 1 upload, step 2 map columns (auto-suggest and saved mappings
per org), step 3 validate (errors per row, fix in place or skip), step 4 duplicate review
(merge into an existing record, create new, or skip), step 5 commit. Two import types:
constituents only, and constituents plus gift history (one gift per row, constituent
columns repeated). Every import is a job with a summary and a one-click rollback.
Starter mappings for a generic spreadsheet, Little Green Light, Bloomerang, Zeffy,
Givebutter and a Stripe payments export.

Done when: a 5,000-row spreadsheet of constituents plus gifts imports in under two minutes
with duplicate review, and rollback removes every created row.

## Design

- The file is parsed in the browser (Papaparse for CSV, SheetJS for XLSX) and never
  stored. Rows go to the API in chunks of 500 as arrays aligned to the header row.
- `import_jobs`, `import_rows` and `import_mappings` hold the work. Each row keeps its
  raw cells, the mapped field values (which "fix in place" edits), the normalized result,
  errors, warnings, a person key, and the ids it created.
- Mapping and validation run in `packages/core/src/import` so the rules are unit tested
  without a database. Dates accept ISO, US formats, month names and Excel serial numbers.
  Money strips signs and commas and refuses refunds and zero.
- Rows are grouped into people by a person key: legacy id, else email, else name and ZIP,
  else name. A file with ten gifts from Dana Rivera creates one Dana Rivera.
- Each person is matched against the organization with the same scoring as the duplicate
  queue. One strong match (score 0.9 or more) is matched automatically; weaker matches go
  to review; no match is created new. The admin can change any of these.
- Commit runs in one database function as the system actor: it creates missing funds,
  campaigns and appeals by name, creates people with their contact details and tags, and
  puts every gift in one posted batch named after the file. Gift entry standards are not
  applied to history. Matched people are not edited, only given gifts.
- Duplicate rescans are deferred during commit and run once per created person at the end.
- Rollback deletes the gifts, the batch, the people the import created, and any funds,
  campaigns or appeals it created that nothing else uses. People who have since gained
  gifts, notes or relationships from outside the import are kept and listed.
- Owners and admins run imports.
